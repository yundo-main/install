# install

설치 절차와 그 실행 도구를 대상별 하위 디렉터리로 관리한다.

절차를 문서로만 남기지 않고 스크립트로 고정해, 지문 대조·검증 순서·최소 권한
기본값이 수행자의 판단에 의존하지 않도록 하는 것이 목적이다.

## 디렉터리 구조

```
install/
├── readme.md                    문서 역할 정책, 디렉터리 구조  ← 현재 문서
├── network-troubleshooting.md   공용 참조 — 연결 실패 시 판별 절차
├── docker/                      Ubuntu 24.04 Docker CE + Swarm
└── k8s/                         Kubernetes 설치
```

`network-troubleshooting.md` 는 특정 설치 절차에 종속되지 않는 공용 참조다.
하위 디렉터리의 단계 문서가 이를 참조한다. 반대 방향 참조는 두지 않는다.

---

## 문서 역할 정책

하위 디렉터리는 아래 역할로 파일을 구성한다. 역할이 다른 내용을 한 파일에 섞지
않는다.

| 파일 | 역할 | 답하는 질문 | 변경 사유 |
|---|---|---|---|
| `README.md` | 인덱스 | 이 디렉터리는 무엇이고 어떤 파일로 구성되며 실행 순서는 무엇인가 | 파일이 추가·삭제될 때 |
| `NN-<concept>.md` | **단계 문서 (자기완결)** | 이 단계는 왜·어떻게 하고, 기대 출력·검증·잔여 위험은 무엇인가 | 해당 단계의 절차·인터페이스·환경이 바뀔 때 |
| `NN-<concept>.sh` | 실행 도구 | (실행 대상) | 구현이 바뀔 때 |
| `<concept>.md` | 주제 문서 | 실행 순서가 없는 횡단 주제 (저작 표준, 통제 색인 등) | 해당 주제가 바뀔 때 |

### 단계 문서 `NN-<concept>.md`

실행 순서가 있는 각 단계는 문서와 스크립트를 **같은 번호·이름의 페어**로 둔다
(`02-docker-ce.md` ↔ `02-docker-ce.sh`). 문서는 그 단계의 근거·실행·옵션·기대
출력·검증·잔여 위험을 **한 파일에 모은다.**

- 스크립트는 절차 설명을 복제하지 않고 헤더에서 자기 단계 문서를 가리킨다.
- **제목 요약**: 모든 `NN-<concept>.md` 는 H1 바로 아래에 이 단계가 무엇을·어디서
  하고 결과가 무엇인지 1~3문장으로 둔다 (`**요약.** …` 형식). `> 역할:` 블록쿼트
  (유지보수자용 구조 계약)와 별개인, 독자용 한눈 요약이다.
- **충돌 시**: 코드가 단계 문서와 어긋나면 문서가 기준이다. 지문 상수·검증 기준이
  갈릴 때 판단을 유보하지 않기 위한 규칙이다.
- 디렉터리 목록만 보고 실행 순서를 알 수 있어야 한다. 순서가 바뀌면 번호를 다시
  매기고 참조를 함께 갱신한다. 번호는 실행 순서일 뿐 의존성 선언이 아니다 —
  전제 조건은 각 스크립트가 직접 검증한다.

> **이전 구조(`plan.md` 근거 / `USAGE.md` 운영 / `README.md` 인덱스 3종 분리)에서
> 전환했다.** 스크립트로 도는 절차를 근거·운영 두 파일로 나누면 같은 명령이 양쪽에
> 복제된다. `docker/04-swarm-cluster.md` 가 이 중복 때문에 먼저 자기완결 단일 파일로
> 통합됐고, 나머지 단계도 같은 방식으로 정리했다. 판단 기준은 **중복이 줄어드는가**다.

### 주제 문서 `<concept>.md`

실행 순서에 들어가지 않는 횡단 주제는 번호 없이 별도 파일로 둔다
(예: `docker/compose-authoring.md`, `docker/controls.md`). 단계 문서와 명령을
공유하지 않고 자기완결이어야 한다.

설치 절차 자체가 다르면 문서가 아니라 **하위 디렉터리**로 분리한다.

### 배치 기준

| 내용 | 위치 |
|---|---|
| 그 단계의 근거·배제한 대안·기대 출력·대조 상수 | 해당 `NN-<concept>.md` |
| 그 단계의 실행 순서·실행 위치·전송 방법·옵션 계약·기본값 | 해당 `NN-<concept>.md` |
| 그 단계의 잔여 위험·통제 범위 밖 항목 | 해당 `NN-<concept>.md` |
| 스크립트로 옮기지 않은 수동 절차 (GUI 설정 등) | 해당 `NN-<concept>.md` |
| 여러 단계에 걸친 통제 원칙·상수·잔여 위험 색인 | `controls.md` |
| 설치 이후 구성 표준, 금지 항목 (횡단 주제) | `<concept>.md` (예: `compose-authoring.md`) |
| 디렉터리 인덱스·실행 순서·명명 규칙 | `README.md` |

## 의존 방향

```
NN-<concept>.md  ↔  NN-<concept>.sh        (문서가 기준)
README.md  →  단계 문서·주제 문서          (인덱스, 역참조 없음)
```

- 스크립트를 삭제해도 절차의 감사 추적은 단계 문서에 남는다.
- **중복 금지**: 스크립트는 절차 설명을, `README.md` 는 단계 상세를 갖지 않는다.
  각 파일 헤더에 자기 역할과 이 경계를 선언한다.

## 스크립트 분리 기준

**실행 주체의 신뢰 경계가 다르면 파일을 나눈다.** 클라이언트에서 실행하는 절차와
대상 호스트에서 실행하는 절차를 한 파일에 두지 않는다.

원격으로 전송되는 스크립트는 **자기완결이어야 한다.** 단독 `scp` 대상이므로 공용
라이브러리 파일을 만들어 참조하지 않는다. 전송되는 아티팩트에 클라이언트 로직이
섞이면 안 된다.

## 하위 디렉터리 추가 기준

- 대상 호스트만 다르면 디렉터리를 늘리지 않고 스크립트 인자로 처리한다.
- 절차 자체가 다르면 별도 디렉터리로 분리한다.
- 절차와 무관한 운영 스크립트는 이 트리에 두지 않는다.

## 정책 적용 현황

| 디렉터리 | README.md | 단계 문서 `NN-*.md` | 주제 문서 | 스크립트 |
|---|---|---|---|---|
| [docker/](docker/) | O | O (00–04) | `compose-authoring.md`, `controls.md` | 00–03 |
| [k8s/](k8s/) | — | `plan.md` (구 구조) | — | — |

`docker/` 의 스크립트는 4개다 — `00-ssh-server.sh`(노드 로컬), `01-ssh-client.sh`
(클라이언트), `02-docker-ce.sh`(Docker CE), `03-compose.sh`(Compose). Swarm 구성은
`sudo` 비밀번호와 지문 육안 대조를 요구해 스크립트화하지 않고
`docker/04-swarm-cluster.md` 에 수동 절차로 뒀다.

`k8s/` 는 아직 `plan.md` 만 존재한다. 스크립트화 시 위 단계 문서 정책을 적용해
`NN-<concept>.{sh,md}` 페어로 재구성한다.
