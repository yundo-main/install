# install

설치 절차와 그 실행 도구를 대상별 하위 디렉터리로 관리한다.

절차를 문서로만 남기지 않고 스크립트로 고정해, 지문 대조·검증 순서·최소 권한
기본값이 수행자의 판단에 의존하지 않도록 하는 것이 목적이다.

## 디렉터리 구조

```
install/
├── readme.md                    문서 역할 정책, 디렉터리 구조  ← 현재 문서
├── network-troubleshooting.md   공용 참조 — 연결 실패 시 판별 절차
├── docker/                      Ubuntu 24.04 Docker CE 설치
└── k8s/                         Kubernetes 설치
```

`network-troubleshooting.md` 는 특정 설치 절차에 종속되지 않는 공용 참조다.
하위 디렉터리의 plan.md 가 이를 참조한다. 반대 방향 참조는 두지 않는다.

---

## 문서 역할 정책

하위 디렉터리는 아래 4개 역할로 파일을 구성한다.
역할이 다른 내용을 한 파일에 섞지 않는다.

| 파일 | 역할 | 답하는 질문 | 변경 사유 |
|---|---|---|---|
| `README.md` | 인덱스 | 이 디렉터리는 무엇이고 어떤 파일로 구성되는가 | 파일이 추가·삭제될 때 |
| `plan.md` | 기준 문서 (source of truth) | 왜 이렇게 하는가, 기대 출력은 무엇인가 | 절차 또는 대상 환경이 바뀔 때 |
| `USAGE.md` | 운영 매뉴얼 | 어떻게 실행하고 어떤 표준으로 구성하며 무엇을 수용하는가 | 스크립트 인터페이스 또는 구성 표준이 바뀔 때 |
| `NN-*.sh` | 실행 도구 | (실행 대상) | 구현이 바뀔 때 |

**스크립트는 실행 순서를 파일명에 붙인다** (`01-`, `02-`, …). 디렉터리 목록만 보고
실행 순서를 알 수 있어야 한다. 순서가 바뀌면 번호를 다시 매기고 참조를 함께 갱신한다.
번호는 실행 순서일 뿐 의존성 선언이 아니다. 전제 조건은 각 스크립트가 직접 검증한다
(예: `03-compose.sh` 는 서명된 저장소 설정 존재를 확인하고 없으면 중단한다).

**문서는 이 3종으로 고정한다.** 설치 이후의 구성 표준(예: compose 파일 작성 기준)도
별도 문서를 만들지 않고 `USAGE.md` 안에 절로 둔다. 문서 수가 늘면 어디에 무엇을
쓸지 판단이 갈리고, 같은 내용이 여러 곳에 복제된다.
설치 절차 자체가 다르면 문서가 아니라 **하위 디렉터리**로 분리한다.

`README.md` 에는 **프로젝트 목적, 디렉터리 구조, 각 파일의 역할만** 둔다.
실행 순서·옵션·위험은 `USAGE.md` 로 분리한다.

### 배치 기준

| 내용 | 위치 |
|---|---|
| 명령의 기대 출력, 지문·버전 등 대조 상수 | `plan.md` |
| 설계 근거, 배제한 대안과 그 이유 | `plan.md` |
| 스크립트로 옮기지 않은 수동 절차 (GUI 설정 등) | `plan.md` |
| 실행 순서, 실행 위치, 전송 방법 | `USAGE.md` |
| 옵션 계약, 기본값 | `USAGE.md` |
| 잔여 위험, 통제 범위 밖의 항목 | `USAGE.md` |
| 설치 이후 구성 표준, 금지 항목 | `USAGE.md` |

## 의존 방향

```
plan.md  →  *.sh  →  USAGE.md
```

단방향이다. `plan.md` 는 스크립트를 참조하지 않으므로 스크립트 없이도 성립한다.
스크립트를 삭제해도 절차의 감사 추적은 남는다.
`README.md` 는 어느 쪽에서도 참조되지 않는 인덱스다.

**충돌 시 우선순위**: 코드가 `plan.md` 와 어긋나면 `plan.md` 가 기준이다.
지문 상수나 검증 기준이 갈릴 때 판단을 유보하지 않기 위한 규칙이다.

**중복 금지**: `plan.md` 는 사용법을, `USAGE.md` 는 근거를, 스크립트는 절차 설명을
갖지 않는다. 각 파일 헤더에 자기 역할과 이 경계를 선언한다.

## 스크립트 분리 기준

**실행 주체의 신뢰 경계가 다르면 파일을 나눈다.** 클라이언트에서 실행하는 절차와
대상 호스트에서 실행하는 절차를 한 파일에 두지 않는다.

원격으로 전송되는 스크립트는 **자기완결이어야 한다.** 단독 `scp` 대상이므로
공용 라이브러리 파일을 만들어 참조하지 않는다. 전송되는 아티팩트에 클라이언트
로직이 섞이면 안 된다.

## 하위 디렉터리 추가 기준

- 대상 호스트만 다르면 디렉터리를 늘리지 않고 스크립트 인자로 처리한다.
- 절차 자체가 다르면 별도 디렉터리로 분리한다.
- 절차와 무관한 운영 스크립트는 이 트리에 두지 않는다.

## 정책 적용 현황

| 디렉터리 | README.md | plan.md | USAGE.md | 스크립트 |
|---|---|---|---|---|
| [docker/](docker/) | O | O | O | O |
| [k8s/](k8s/) | — | O | — | — |

`docker/` 의 스크립트는 6개다 — `01-ssh-setup.sh`(클라이언트), `02-install.sh`(Docker CE),
`03-compose.sh`(Compose), `04-node-prepare.sh`(복제본 신원 분리),
`05-swarm-init.sh`(매니저), `06-swarm-join.sh`(워커).
Swarm 은 Docker CE 설치의 연장이므로 디렉터리를 나누지 않고 번호를 이어 붙였다.

`k8s/` 는 `plan.md` 만 존재한다. 스크립트화 시 위 정책을 적용한다.
